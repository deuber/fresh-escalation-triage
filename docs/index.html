Why this work

In fresh, a wrong order ends up in the dumpster or on an empty shelf

Too much

Order too much and it goes into the dumpster by Friday. Shrink comes straight out of a margin that is already thin.

Too little

Order too little and a shopper leaves without it, and may do the rest of their shopping somewhere else.

The grocer's profit is the reason the product gets bought, and I take that seriously. What draws me to this role is that in fresh, profit and waste are the same problem: every pound that sells instead of being thrown out is margin for the store and food that got eaten. I want to be on the team that makes that happen.

That's why the support side interests me. When an escalation is fixed at its root, one store's order isn't the only thing fixed. Waste goes down at every store the same defect touched. Each ticket below ends with what it costs, in pounds or in empty shelves.

Work a ticket

How it works: every ticket has exactly one layer at fault. Your job is to find it.

  1. Pick a ticket from the list on the left.
  2. Run the checks. Click each of the four layer cards under "Check each layer." Three come back Normal. One comes back Problem.
  3. Call the root cause. Choose the layer whose check showed the Problem. Get it right and you'll see the cause, who fixes it, what I'd build to prevent it and what it cost.

Tip: rule out the data before blaming the model.

From escalation to Tier 1 skill

      
Two of the four tickets above can be solved with two queries and a rule. That makes them
        good candidates for a Claude skill that Tier 1 runs before escalating. Here is a sketch of one, and of
        where it should stop.

    

    

      
---
name: over-order-triage
description: Use when a store reports an order far larger
  than usual for one item. Runs the feed-freshness and
  item-history checks before anyone escalates.
---

# Over-order triage

1. Get store_id, item_id and order date from the ticket.
2. Run feed_freshness.sql for the store.
   inventory_on_hand older than 24 h → stale feed.
   Go to step 5.
3. Run item_history.sql for the item and banner.
   units_per_case changed by more than 50% in the
   last 14 days → mapping defect. Go to step 5.
4. Neither found → escalate to Support Engineering
   with both results attached. Don't guess at the model.
5. Draft the store reply and the internal note.
   Log ticket ID, finding and outcome.

      

        
Where the automation stops

        
    
          
  • It reads and drafts. It doesn't act. It never edits an order or the item master. A person approves anything that goes to a store.
    • 
          
  • It only answers what data can prove. A stale feed or a changed case size shows up in a query. A forecast miss is a judgment call, so the skill hands it to a person.
    • 
          
  • It shows its evidence. Every answer includes the query results, so Tier 1 can check it rather than trust it.
    • 
          
  • It's measured. Each run logs its outcome, so the deflection rate is counted, not estimated, and a wrong answer becomes a test case.
    •

Things that trip people up

    

      
A stale feed looks like a bad model
The model forecasts correctly, then orders against an on-hand number from three days ago. Check freshness before accuracy.

      
Joins that quietly duplicate rows
An item with two case-size history rows doubles every sales row it touches. Count before and after each join.

      
UTC versus store time
A timestamp stored in UTC lands on tomorrow's date for anything approved after 4 PM Pacific in the winter.

      
The convenient table isn't the source of truth
Validate against the store's physical count or the retailer's feed, not a derived table that inherited the error.

      
A model miss isn't a bug
Nothing to hotfix. The job is to package evidence so the science team can see the pattern across stores.

      
Fix one store, then count the rest
Before closing, run the same query across every store to size the impact. That number decides the priority.
